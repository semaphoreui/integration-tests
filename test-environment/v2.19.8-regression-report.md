# Semaphore v2.19.8: terminal task status precedes output/stage persistence

- **Check date:** 2026-08-19
- **Version:** `semaphoreui/semaphore:v2.19.8` (`3449a04f3bfa2522ec7fd60803f71b578c39f6b4`)
- **Status:** reproducible locally, not confirmed by the latest Linux CI
- **Component:** task runner / task logger / task output persistence

## Summary

Semaphore may publish the terminal task status (`success` or `error`) before writing of output/stages has finished. A client that reads the output immediately after the terminal status gets incomplete diagnostics or a truncated output of a successful task.

## Scenario 1: Git stderr loss

1. Create a repository with a non-existent branch `bookwright-missing-ref`.
2. Run the template and wait for task status `error`.
3. Immediately read `GET /api/project/{project_id}/tasks/{task_id}/output`.

Expected: the output contains the clone failure and the name of the problematic branch.

Actual result in failed runs:

```text
Cloning Repository file:///fixtures/ansible
Failed updating repository: exit status 128
Failed to run task: exit status 128
```

The branch name and Git stderr are missing. In five forced reruns on SQLite the scenario failed 3 times. The same failure was obtained in the full SQLite core run and in the production-like run with `semaphoreui/runner:v2.19.8`. The PostgreSQL, MySQL, and MariaDB core runs in this series passed, which confirms the non-determinism.

## Scenario 2: `success` before output finalization

The SQLite and PostgreSQL upgrade profiles:

1. Create a linked fixture on `v2.19.7`.
2. Restart the server on `v2.19.8` with the same database.
3. Successfully read the project, access key, repository, inventory, template, schedule, and the old task output.
4. Re-run the saved template and wait for `success`.
5. Immediately read the task output.

In both dialects the output is cut off after:

```text
PLAY [Semaphore test fixture] **************************************************
```

The expected marker `semaphore-bookwright-smoke-ok` and the play recap are missing, even though the task already has `success`.

After the task is deleted during test cleanup, the server keeps writing the stage and logs:

```text
SQLite: constraint failed: FOREIGN KEY constraint failed (787)
PostgreSQL: insert or update on table "task__stage" violates foreign key constraint "task__stage_task_id_fkey" (23503)
```

## Expected Contract

- the terminal task status is published only after all output and stages have been written;
- immediately after the terminal status the API returns the complete, stable output;
- after a terminal task is deleted there are no late writes to related tables and no FK errors;
- a Git clone failure preserves the stderr needed for diagnostics.

## Check in GitHub Actions

After updating the test repository to `v2.19.8` on 2026-08-19, three Linux workflows were run:

- CI: quality gate and `core-sqlite-local` — passed;
- configuration matrix: PostgreSQL, MySQL, MariaDB, and persistent remote runner — passed;
- release upgrade: SQLite and PostgreSQL — passed.

In these runs the Git stderr loss and the early finalization of the upgrade task did not reproduce. Therefore the observation cannot be considered a general blocking regression of `v2.19.8` without additional statistics. The separate upgrade workflow and the diagnostic assertions are kept as monitoring; the local evidence is not removed.

## Reproduction Commands

```bash
test-environment/profile up core-sqlite-local
test-environment/profile test core-sqlite-local --no-daemon --rerun-tasks \
  --tests io.bookwright.tests.semaphore.RepositoryGitTest.missingBranchFailsWithUsefulOutput

test-environment/profile upgrade-test upgrade-sqlite-local
test-environment/profile upgrade-test upgrade-postgres-local
```
